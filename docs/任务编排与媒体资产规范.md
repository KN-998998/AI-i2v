# 任务编排与媒体资产规范

本项目吸收同类开源项目的流程设计，但不复制外部代码。当前流水线保持现有 React Flow + FastAPI 架构，并把媒体生产拆成可恢复的阶段：

```text
素材上传 → 图片处理 → 提示词装配 → Kling 生成
→ 轮询 → 下载 → 本地规则评分/入库 → 多片段合成 → Qwen TTS/BGM/文字
```

## 异步任务状态

`web/services/task_contract.py` 是三类任务共用的持久化契约。任务 JSON 保留原有字段，同时增加：

- `task_type`：`image_processing`、`kling_generation` 或 `video_composition`。
- `status_version`：任务记录格式版本，便于以后迁移。
- `phase`：供前端显示的机器可读阶段。
- `events`：最近 40 次状态/阶段变更，用于排查任务停在哪一步。
- `retry_count` / `max_retries`：为后续有限重试和队列调度预留。

标准状态为：

```text
queued → running → polling → downloading → analyzing → done
                         ↘ retrying ↗
任意运行中状态 → error
```

图片处理不经过 `polling` 和 `downloading`；合成任务从 `queued` 进入 `running`。旧任务只要仍处于 `queued` 或 `running`，重启恢复逻辑仍然有效；新增加的 `polling`、`downloading`、`analyzing`、`retrying` 也会被恢复。

## 媒体资产规则

- Kling 返回地址只作为临时结果使用，任务完成后立即下载到 `output/canvas_clips/`。
- 下载完成后才执行视频质量分析，并把评分、警告、来源任务和版本信息写入片段 manifest。
- 草稿引用 `assetId` 和 `clipVersion`，重新生成会产生新版本，不覆盖历史文件。
- 合成只消费本地、经过预检的片段；不在合成阶段重新猜测外部 URL。

## 后续扩展边界

下一阶段可以在不改变页面 API 的前提下增加：

1. 基于 `retry_count` 的有限重试和退避（当前已用于 Kling 下载/分析阶段）。
2. Kling 轮询、下载、评分的独立后台队列和并发限制。
3. 任务列表页、错误重试按钮和每阶段耗时统计。
4. A/B 成片方案和按菜品类别的推荐策略。

当前阶段没有把外部模型评分接入生产链路；质量评分仍是本地规则评分，人工确认仍是成片发布前的必要环节。
